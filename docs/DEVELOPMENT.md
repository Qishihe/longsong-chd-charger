# 从零开始：一个校园充电桩查询站的诞生

> 这份文档记录了一个真实项目从「什么都没有」到「双站上线」的全过程：
> 怎么定的技术路线、哪一步走错了、为什么改主意、哪些坑是同一条路上必然踩的。
>
> 时间跨度 2026-10-18 ~ 2026-10-25，共 8 天、92 次提交。
> 如果你也想给自己学校做一个类似的工具，这里的过程比结论更有用。

---

## 0. 起点：一个具体的小麻烦

长安大学渭水校区的共享充电桩分布很散 —— 北门一长排、朝晖体育场南两段弧、20 号楼 24 台、物业服务中心 12 台，合计 **109 台**。
每台 4 个插口，理论上 436 个位子。

但「理论上」这三个字在晚上七点毫无意义。真实体验是：

1. 从宿舍走到最近的桩区，5~10 分钟；
2. 到了发现全被占了；
3. 再走到下一个区域，还是满的；
4. 回宿舍。

问题不在于「没有空位」，而在于**决策前看不到状态**。运营商的小程序能查，但要扫某台桩的码才看得到那一台 —— 它天生不是为「找空位」设计的。

所以目标定得很小、很具体：**一个页面，打开就知道现在哪里有空位。** 不装 App、不注册、不登录。

---

## 1. 第一步不是写代码，是搞清楚数据从哪来

动手前先花了一整天做侦察，因为这类项目九成败在数据源，不是界面。

### 1.1 先看别人怎么做的

找到汕头大学的开源项目 [stu-charge-watch](https://github.com/zhuangchuyuan86-bot/stu-charge-watch)，
它服务的是另一个充电 SaaS（`wx.isfdz.com`）。它的做法很聪明：

```
GET 首页 → 解析 static/js/index.<hash>.js
        → 正则挖出 app_id / app_secret（凭证硬编码在前端包里）
        → sign = md5(参数按 key 升序拼接 + secret)
        → 直接调 POST api/equi/.../getLineInfo 拿到 [{num, state}]
```

`state` 码表也拿到了：`1 空闲 / 2 占用 / 0 粘连故障 / 5 高温 / 6 过流 ...`。

### 1.2 然后确认这条路在本校走不通

本校用的是竹芒（街电）体系。逐项验证后，结论是**汕大的套路完全不可复制**：

| 环节 | 汕大 | 本校（竹芒） |
|---|---|---|
| 客户端形态 | Vue H5 + 后端服务 | 微信原生小程序 |
| 鉴权 | 前端硬编码 secret，`md5` 签名 | `wx.login` → 服务端 session |
| 前端可挖的东西 | 有 secret | **无**，secret 不在前端 |
| 扫码落地页 | — | Nuxt SSR 营销页，`payload.js` 内容仅 `data:[{}]`，不含任何设备数据 |

扫码落地页这一项是决定性证据：`https://charging.jiedian.live/ssr/wxprogram/?id=XLA23805` 里，
桩号 `XLA23805` 出现 **0 次**，页面只做 `<wx-open-launch-weapp>` 跳转，真正的实时状态在
`admin.sdbattery.com`（代理商后台，需登录）。

顺带一条硬约束：汕大那仓库**没有 LICENSE 文件**，按其 `LICENSE-CHOICES.md` 自述属「保留所有权利」，
连整套复制公开都不合规。所以从一开始就确定：**只看思路，代码全部重写。**

### 1.3 转折点

穷举了几条干净路子都没有结果后，剩下的唯一可行方案是：**由使用者自己抓一次小程序请求，取出那串 JWT，浏览器拿它去问平台。**

这条路合规风险最高、稳定性最差（token 约 7 天过期），但它是唯一能真的跑起来的。
于是整个项目的技术形态从此被决定：**前端为主、凭证在用户浏览器里、不做任何账号操作、只读。**

## 2. 打地基：先写接口，不写页面（10-18）

第一个 commit 不是页面，是一个**可插拔的采集骨架** `campus-pile-kit/`：

```python
# 适配器契约 —— 整个项目最重要的一行设计
read_ports(device_id) -> [{"num": 1, "state": 2}, ...]
```

只定义这一个方法，然后立刻写两个实现：

- `adapters/mock.py` —— 生成假数据，让前端在没有真实接口时也能开发；
- `adapters/csv_export.py` —— 读 CSV，对应「拿到运营商后台导出」这条最稳的落地路径。

**为什么先做这一步**：当时并不能确定最终能不能抓包成功。如果先写界面，一旦数据源换成 CSV，
前端要跟着大改；而先定死「不管数据从哪来，都长成这个形状」，后面无论走哪条路，上层都不用动。

事后看这是整轮开发**性价比最高的一个决定** —— 后面数据源换了三次（mock → 抓包直连 → 服务端反代），
上层渲染逻辑一行没改。

## 3. 形态切换：从「Python 服务」到「纯前端单页」（10-19 ~ 10-20）

骨架跑通后，很快就撞上第一个架构决策。

原设计是：Python 服务端持有凭证、代查平台、前端只负责渲染。这样凭证安全、也不用用户抓包。
但有两个问题：

1. **得有人养一台服务器**。学生项目没有预算，也没有运维；
2. **一个人持有凭证 = 所有人共用同一个出口 IP**，而平台的限流正是按出口 IP 算的（这个坑后面炸得很响）。

最终选择：**把整个应用做成一个前端单页，没有自建后端。**

代价与收益：

| | 服务端方案 | 纯前端方案（采用） |
|---|---|---|
| 运维成本 | 需要一台常开的机器 | 静态托管，免费额度足够 |
| 凭证 | 服务端持有，用户无感 | 用户自己提供，存 localStorage |
| 风控 | 所有请求同一个出口 IP | 分散到每个真实用户 |
| 账号安全 | 服务端能碰到 | 数据不出浏览器 |

代价是**用户体验变差**（要抓一次包）。为了把这个代价压到最低，专门写了 `help.html`：
一张带标注的图文教程，从装证书到找到那行 `Authorization`，一步一步截图。

同一时期地图从「一张静态总览图」升级成高德 JS API —— 静态图的问题是桩位一改就得重画，
而地图可以只改数据。这部分踩的坑很典型：高德 2.0 **没有** `AMap.GeoJSON` 类，
而调用写在初始化末尾，前面一抛错后面三个图层全部静默不渲染 —— **没有任何报错，就是图上是空的**。

## 4. 最难的部分：凭证（10-20 ~ 10-22）

token 约 7 天过期。一个人用，7 天抓一次包可以忍；但一个班几十个人用，每个人各自抓包就很不现实。

于是做了第一次尝试：**用云数据库分发凭证**。

### 4.1 第一次尝试失败

方案是标准的：站长上传凭证 → 存云端表 → 同学打开页面拉取。
上线没多久就崩了 —— 云端返回 `503 DATABASE_RESOURCE_ISOLATED`，数据源被整体隔离，彻底不可用。

> 这一课很直接：**依赖一个你无法控制的外部服务，就得准备好它随时消失。**
> 而正确反应不是「等它恢复」，是把它换掉。

### 4.2 换成 KV 信箱，并且让服务端看不到明文

迁移到 Cloudflare Pages 后，用 KV 顶上「信箱」角色，但加了一层设计：

```
站长在 /admin 输入凭证
  → 浏览器里 PBKDF2-SHA256（20 万轮）派生密钥
  → AES-GCM 加密
  → POST /api/cred，KV 里只存密文

同学打开页面
  → GET /api/cred
  → 比本机版本新才解密
  → 换上 → 刷新
```

关键点：**服务端的 Worker 从头到尾只搬运密文**。即使 KV 被读、Worker 日志泄露，也拿不到明文凭证。
写操作另有一道口令（存在 Cloudflare Secret 里，不写进任何文件）。

这里埋了一个后来踩到的坑：**`/api/*` 必须排除出 Service Worker 缓存。**
SW 对静态资源是「缓存优先」，如果不排除，手机会永远读到第一份密文 —— 换凭证等于白换，
而且**零报错**，最难查的那类问题。

## 5. 真正的对手：平台风控（10-23）

10-23 出现了一次线上 P0：页面**一直转圈，刷新不停也不更新**。

排查顺序完全走错了三遍：

1. 先怀疑前端 —— 服务端的并发/缓存逻辑看起来都对；
2. 再怀疑自锁 —— 周期性定时器 + 忙时排队 + 慢任务，确实能造成永久自锁（这确实也是个真 bug，修了）；
3. 最后才怀疑到网络层 —— **直连平台 109 台/分钟，全部 TCP 超时。**

注意症状：**不是 401，不是 429，是 TCP 超时。** 这一点极具误导性：

| 现象 | 真实含义 | 容易误判成 |
|---|---|---|
| HTTP 401 | 凭证失效 | 「凭证对不对」 |
| HTTP 429 | 被限流（明示） | 「降频就好了」 |
| **TCP 超时** | 被风控在更底层掐断 | 「平台挂了 / 我代码有 bug」 |

### 解法是三层叠加

1. **降频**：从「每 60 秒全量 109 台」改成 10 分钟一轮；
2. **批量**：不再逐台打，改成服务端一次汇总请求（Worker 代打 + 按桩位 id 的全站共享缓存 300s）；
3. **反代层加缓存**：Worker 的限流按调用方 IP 分桶（30 次/分钟），反代出去全站共用一个出口 IP
   → 很容易撞额度。所以反代层自己再做一层按 id 的缓存 + 在途请求合并，上游 429 时用旧缓存顶上。

最后收敛到的参数是：`并发 6 / 分批 12 / 双泳道`。
实测 18 并发时成功率掉 35% —— **这个数字是靠反复试出来的，不是拍脑袋定的。**

## 6. 双轨与工程纪律（10-20 ~ 10-25）

到 10-20 之后，改动开始有「不能直接给所有人看」的需求，于是引入双轨：

```
preview.html  内测版（带密码门禁）
index.html    正式版
```

两者不是手抄两份，而是**脚本生成**：`sync_index_v214.py` 从 `preview.html` 出发，
做 14 处固定替换（去门禁、去内部标记、换引擎文件名、改版本号），
**每一处都断言「只命中一次」** —— 宁可停下报错，也不产出半成品。

### 为什么值得这么麻烦

因为手抄两份一定会漂移，而漂移的后果极难发现。这个项目就真实发生过：

- **只发内测，正式版却偷偷变了**：两版共用一个 js 文件，SW 是 stale-while-revalidate，
  正式版用户第二次打开就拿到了新 js。从此定规矩：*可见的改版走文件级隔离（`map-amap-preview.js`），验收后再覆盖、两版同升。*
- **升了 `?v=` 但内容没换**：内测引擎 `v6→v7`，正式版文件内容换新了但 URL 没变，
  SW 继续喂旧 js，页面调 `engine.viewInfo()` 直接失败。现在脚本第 0 步会比对引擎内容，变了就必须升 `?v`，否则断言失败。

### 守门检查代替 CI

没有 CI（纯静态站也没法跑），改成一个 44 项的静态断言脚本 `check_dual_track.py`，每次发布前必跑：

```
[✓] 两版函数体逐字节一致（13 个关键函数）
[✓] 站点目录没有 Markdown 文档、没有 versions/（历史快照不该公开托管）
[✓] serve_gzip.py 发 Content-Encoding: gzip / 带 Vary
[✓] serve_gzip.py 反代 /api/* 且带浏览器 UA、改写 Origin
[✓] 服务端屏蔽自身源码（不对外提供 serve_gzip.py）
```

### 回退要整包

```
release-2026-10-25-v2.31  →  index.html / preview.html / map-amap.js /
                             map-amap-preview.js / map-data.js / sw.js / serve_gzip.py
```

**只换 html 会半新半旧** —— 版本号对上了但引擎是旧的，比不换还糟。
每个回退点都记着当时线上真实在跑那套文件的 md5，恢复前先核对快照自身没被改过。

## 7. 几次「差点发布出去」的事故

这几条是整轮开发最贵的学费，每一条都曾经在线上真实发生过。

### ① 字符串键没归一化 → 12 台桩静默消失

外部给的桩位清单里混着 **U+2011（不换行连字符）**，和仓库里的 **U+002D（普通连字符）** 肉眼完全一样。
按字符串精确比对查不到 → 掉回「非北门即朝晖」的二分类兜底 → 12 台挤进 36 个弧位 → **静默丢弃**。

教训：**任何来自外部的字符串键，比对前统一 `normKey()`。** 改名要同时改 schema 迁移 + 旧名别名 + 丢弃规则，
五处缺一就会丢桩。

### ② 注释里出现 `*/` → 整页白屏

CSS/JS 块注释里写路径 `map-amap-preview.js` 没问题，但一旦写成 `versions/*/` 这种，
`*/` 会提前闭合注释，后面整段代码变成语法错误 —— **页面白屏，控制台一行报错都没有。**

### ③ Service Worker 缓存了接口

见 4.2。手机永远读到第一份密文，换凭证白换，零报错。

### ④ 域名拼写靠语感 → 整个排查方向错

平台真实域名是 `union.zhumanggroup.com`（**zhumang**，竹芒）。
有一次「凭印象修正」成少一个字母的 `zhuanggroup`，结果教程、脚本、测试全错，
探针跑出「平台请求 0 次」的假结论，差点据此判定「直连方案不可行」。

正确做法：**别自己解码 base64 猜域名，在页面里 `evaluate(API_BASE)` 直接读。**

### ⑤ 本机网络 ≠ 用户网络

开发机的出口被平台限流，40~52 次请求全部 22 秒无响应，但同一时刻走反代 11 秒就能取到数 ——
说明**平台在线，是本机出口的问题**。

这件事的教训不是技术性的：**「我这儿不行」不等于「用户那儿不行」，也不等于「代码有问题」。**
所以直连方案上线后，仍保留了 `?pileproxy=1` 这个逃生口。

## 8. 最后一步：两个站

到 10-25，站点同时跑在两处：

| | Cloudflare Pages | 自建服务（workbuddy.host） |
|---|---|---|
| 定位 | 主站，Worker + KV 都在这里 | 备用站 / 国内访问更快 |
| 服务 | 纯静态 + Worker | `serve_gzip.py`：静态 + gzip + `/api` 反代 |
| 首屏 ttfb | 0.90s（跨境） | **0.18s** |

`serve_gzip.py` 看起来只是「一个静态服务器」，实际上它是**唯一让第二个站能用的东西**。
它必须做三件平台本身不做的事：

1. 发 gzip（295KB → 105KB）；
2. 反代 `/api/*`，否则 `POST /api/pile` 直接 **501**，页面「一直转圈一个桩都查不到」；
3. 伪装浏览器 UA + 改写 Origin —— Cloudflare 会按签名拦 `Python-urllib`（返回 Error 1010 的 HTML 错误页），
   Worker 里还有 `origin !== url.origin → 403` 的判断。**漏一件，上游就全挂。**

还有一条只有踩过才知道的：**平台发布是增量覆盖，本地删掉的文件不会从云端消失**（没有删除接口）。
清理旧文件后必须同步加进服务层的屏蔽清单，否则 `preview-v3.html` 这类废弃原型会在公网上继续返回 200。

## 10. 如果重来一次

**会保留的**

1. **先定接口、后写界面。** 数据源换了三次，上层一次没改。
2. **双轨 + 脚本生成正式版 + 逐项断言。** 手抄两份必漂移，而且漂移是静默的。
3. **整包快照回退。** 出事故时最值钱的不是「怎么改回去」，是「确定能改回去」。
4. **守门脚本代替 CI。** 44 条断言在大半个月里拦下了好几次准备发布的错误。

**会改的**

1. **更早承认「这个数据源不可靠」。** 抓包取 token 这条路，token 7 天过期、
   接口随时可能变、还有风控。一开始就该把它当「临时方案」而不是「架构」，并尽早准备
   「找学校后勤要只读后台」这条零风险路线。
2. **不碰共享出口 IP 的代理。** 反代方案虽然省事，但把全站流量压在一个出口 IP 上，
   等于主动去撞平台的限流额度，后面为了绕开它加了一整层缓存。
3. **域名、API 路径一律从代码里读，不靠记忆和语感。** 那个少一个字母的域名浪费了大半天。

## 11. 这个项目最终长成什么样

```
109 台桩 / 4 个分区 / 436 个插座
├─ 纯前端单页，无构建、无框架、无 npm
├─ 双轨发布：内测门禁 → 脚本生成正式版
├─ 凭证：浏览器端 AES-GCM 加密 → KV 只存密文
├─ 离线可用：SW 缓存外壳与底图
├─ 44 项守门 + 7 个离线冒烟测试 + 整包回退
└─ 两个站：Cloudflare Pages + 自建 gzip 服务
```

从「走到桩前发现全满了」到「出门前看一眼手机」，中间是 8 天、92 次提交、
和一份记录了几十条坑的运维手册。

如果这份文档能让你少踩其中两个坑，它就值了。
